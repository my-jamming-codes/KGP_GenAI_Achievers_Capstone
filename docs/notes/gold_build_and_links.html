build_gold.py: what it writes and how the files link into the application

One script, run once, produces the 12 sample loan applications that the app shows and the 80 test questions that the evaluation asks. They are built together so every test question has a known right answer on those same applications.

The big picture

The application never reads gold_queries.jsonl or answer_key.json. Only eval/run_eval.py reads the questions, and nothing reads the answer key at all except people. That keeps the test honest: the agent is never shown the answers.

One application, followed through: HL-2043

A Lakeside Housing Finance loan of ₹64 lakh on a ₹76 lakh property, with a guarantor whose disclosure was not recorded. Here is every place it appears.

3In the app

src/app/store.py, then main.py

The Work queue lists HL-2043. Opening it shows the 8 tabs. "Run RBI rule check" turns the file into a Case and runs the agent. The tools work out the LTV as 64 ÷ 76 = 84.2%, against the 80% cap for loans of ₹30 to ₹75 lakh. The card for LTV cap shows Breached, citing HFC-MD/58. The guarantor card shows Needs information.

Where the 80 questions come from

Two shapes of question

Application questions (25): "Run the full RBI rule check on application HL-2043…". They point to one of the 12 saved files. Some also carry the open tab, as if the officer shared that screen.

Described-case questions (34): a case written out in the question, with no saved file. The script starts from one standard case and changes only what the question needs.

Neither (21): plain rule lookups and general refusals such as "Approve this loan.", which need no case.

Q047:  same, but lender_type="bank"

How dev and test are chosen

Within each type, every fourth question becomes a development question (every fifth for scenarios). That gives 20 dev and 60 test, spread across all types. Dev is used to pick a prompt strategy. Test is run afterwards as a check.

The script stops with an error if the counts are not exactly 15, 30, 15, 10 and 10 (80 in all, 25 on applications) or if dev is not 20.

Why the labels can be trusted

The expected statuses and paragraphs were typed by hand from the verified rules, not produced by the app's own tools. If the labels came from the same code being tested, a bug would pass its own test.

At the end, the script switches the output files to read-only, so they can't be edited by accident.
